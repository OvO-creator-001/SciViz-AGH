# 项目交接规范

## 1. 不覆盖原有版本

- 正式交接版本使用 `releases/vX.Y.Z/`，每个版本号只允许创建一次。
- 已被 Git 跟踪的 `releases/` 子目录不得修改、删除、移动或复用。纠错必须发布新补丁版本，例如 `v1.2.0` 的修正写入 `v1.2.1`。
- `main` 禁止强制推送；不得改写已共享的 Git 历史。
- 二进制大产物不直接替换；使用新文件名（含版本或内容哈希），并在版本清单中记录 SHA-256。
- Git tag 与 GitHub Release 均采用 `vX.Y.Z`。已发布 tag 禁止移动或覆盖。

Git 本身会保留提交历史，但这不能替代不可变快照；两者都必须保留。

## 2. 每次更新必须记录技术细节

每个 PR 必须新增且只能新增自己的 `changes/YYYYMMDD-HHMM-简述.md`。条目至少包含：

- 变更摘要和类别；
- 修改的组件、文件与关键实现；
- API、配置、数据结构或依赖变化；
- 兼容性及迁移步骤；
- 验证命令、测试结果和可复现证据；
- 已知限制、风险与安全影响；
- 回滚方式；
- 作者、日期及关联 Issue/PR。

“优化代码”“修复问题”等无法复现或审核的描述不合格。

## 3. 正式交接清单

交接负责人必须确认：

- [ ] 新版本号未被使用，符合语义化版本规则。
- [ ] `changes/` 有本次更新的技术细节。
- [ ] `CHANGELOG.md` 已汇总用户可见及技术影响。
- [ ] 源码、测试、文档和证据已按分类放置。
- [ ] 测试命令、运行环境和依赖版本已记录。
- [ ] 新增 `releases/vX.Y.Z/MANIFEST.md`，列出提交 SHA、文件清单与校验值。
- [ ] 密钥、Token、个人数据和受限论文原文未进入仓库。
- [ ] 接手人按 README 成功复现并在交接记录中签收。

## 4. 分支与审查

- `main` 只接受 PR，不直接推送。
- 分支命名：`feat/*`、`fix/*`、`docs/*`、`test/*`、`ops/*`、`release/*`。
- 一个 PR 聚焦一种主要内容分类；跨分类修改必须解释依赖关系。
- 至少一名非作者完成审查后方可合并。
- 禁止包含秘密信息；发现泄漏时应立即吊销凭据，并以新提交移除，不能仅靠删除旧文件。

## 5. 版本策略

- `MAJOR`：不兼容的 API、数据或交互变更。
- `MINOR`：向后兼容的新能力。
- `PATCH`：向后兼容的修复、文档或小型改进。

版本快照用于交接与审计，不应成为日常开发目录。日常修改位于分类后的活动目录，正式交接时再生成新快照。
